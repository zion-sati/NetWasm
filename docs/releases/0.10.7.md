# NetWasm 0.10.7: SIMD, a loop vectorizer and faster generated code

NetWasm 0.10.7 is available on NuGet.org.

This release is a performance round. `Vector128<T>` and `Vector<T>` are
hardware accelerated on WebAssembly SIMD, CoreLib's vectorized helpers take
their vector paths, and the compiler vectorizes ordinary C# loops. Across
2,202 of dotnet/performance's micro-benchmarks, its vector and span benchmarks
included, an `O3` application takes 0.45 of Mono AOT's time. On the 464 runtime
benchmarks that 0.10.6 also runs, it takes 0.43 of 0.10.6's time.
With NetWasmGC the full transaction workload takes 29.7 ms, less than
desktop .NET 11 NativeAOT's 32.1, and the [performance page](../performance.md)
has every workload, its Mono AOT and desktop figures, and how to reproduce
them.

It also makes WIT bindings follow the component model's own names for
interfaces, which changes generated bindings. Bindings that a `NetWasmWit` item
generates update on the next build; regenerate bindings made with
`netwasm-wit-bindgen`, and update `NetWasm.System.Net.Http` to 0.10.7, whose
earlier versions carry bindings this release rejects.

## SIMD

- `Vector128.IsHardwareAccelerated` and `Vector.IsHardwareAccelerated` are
  true. `Vector128<T>`, `Vector<T>` and `System.Runtime.Intrinsics.Wasm.PackedSimd`
  lower to Wasm SIMD instructions, and vector values live in `v128` locals
  rather than memory.
- CoreLib's `MemoryExtensions`, `SpanHelpers`, the `SearchValues` byte and
  char searchers, `Ascii`, `Base64`, `BitConverter`, `HexConverter`, `Guid`,
  `Vector2`/`3`/`4`, `Plane`, `Quaternion` and the matrix types are .NET 11's
  own code, so span searches, comparisons and these types take their vectorized
  paths.
- `Vector2`, `Vector4`, `Quaternion` and `Plane` values live in `v128` locals
  too, and `AsVector128` and `AsVector2`/`3`/`4` convert between them and
  `Vector128<float>` without a trip through memory.
- On dotnet/performance's vector benchmarks, `System.Numerics` vector code takes
  0.39 of Mono AOT's time and `System.Runtime.Intrinsics` code 0.35.
- `MultiplyAddEstimate` on `float`, `double` and their vectors rounds the
  product before adding the addend, as Mono does, so a multiply-add costs a
  multiply and an add. Desktop .NET fuses them on hardware with FMA, which can
  change the last bit; see [Spec deviations](../spec-deviations.md).
- Case-insensitive ordinal search (`OrdinalIgnoreCase`) and UTF-8/UTF-16
  transcoding still run NetWasm's scalar code.

## Loops

- Element-wise loops run as `Vector128` loops when every access is in bounds
  and the arrays cannot overlap, then finish with the original loop
  (`NetWasmManagedLoopVectorization`, on at `O2` and `O3`).
- Loops that sum, take the minimum or maximum, or xor, or and and elements of
  an array or span fold the whole range at once; fill and copy loops run as
  bulk operations; large array initializers are one copy from static data.
- Pure `Math` calls of values a loop does not change are computed once ahead
  of the loop. Loops that only repeat their first iteration run it once, and an
  element a loop updates in place stays in a local.

## Code generation

- Inlining, struct and object scalar replacement, value tuples split into
  locals, devirtualization by receiver type, static `Type` objects, delegate
  dispatch by branch table, and fewer initialization and array-store checks.
- `Unsafe.BitCast` between values Wasm holds in registers reinterprets them in
  place.
- A struct passed to a call is read where it is instead of copied first, and
  struct locals that hold no object references are no longer registered with
  the collector.
- Arithmetic on constant vectors is computed at compile time, as constant scalar
  arithmetic already was, so a NaN it produces is the canonical NaN rather than
  the one the hardware would propagate. WebAssembly permits either; see
  [Spec deviations](../spec-deviations.md).
- Math: musl's and Arm's `exp`, `log`, `pow`, `fma`, sine and cosine, and
  fdlibm's inverse trigonometry, with their tables in constant data; `SinCos`
  shares one argument reduction.
- `decimal` arithmetic is .NET 11's.
- A few loops whose floating value stays live across a later call run slower
  than in 0.10.6, such as dotnet/performance's NewtR (1.9 times): the value is
  now a Wasm local, which Wasmtime keeps in a stack slot inside the loop.

## Garbage collection

- Combining and removing delegates, `Array.Clone`, slicing an array with a
  range, `Array.Copy` into an `object[]`, `RuntimeHelpers.GetObjectValue` and
  `Nullable.GetUnderlyingType` keep their caller's objects alive while they
  allocate. A collection during one of them could free an object the caller
  still held, such as a multicast delegate's new invocation list, and the object
  that reused its memory later failed a cast or a virtual call. Whether it
  happened depended on when collections ran, so unrelated code changed it
  (issues #144 and #146; `Array.Clone()` could free the array a local held).
- Objects held only through a span or reference to a local or argument stay
  alive: the elements of a `params ReadOnlySpan<T>` argument or a collection
  expression, an inline array a callee reads or fills, and whatever a ref struct
  points into. A collection while such a callee ran could free them; issue #144's
  page then failed in `Node.AddChild`.
- A struct method's receiver keeps what it points into alive, such as a boxed
  enumerator an interface call reaches, and a `fixed` statement keeps the object
  it pins alive until it ends.
- Every compiler test that runs a program also runs on the real runtime with a
  collection before every allocation, under both collectors, before a release.

## Compiler fixes

- Virtual, interface and constrained calls run the method .NET runs (issue
  #147). Before, these bound the wrong method: a `new` method that hides an
  interface implementation without re-declaring the interface, an override of
  an intermediate `new virtual` method, a covariant override three or more
  levels deep (as a record's `Clone`, which `with` uses), and a default
  interface method overridden in a derived interface.
- Creating an object whose type has an explicit static constructor runs that
  constructor even when nothing reads the object (issue #148). At the default
  `Oz` level and in Debug, `new Plugin();` was removed together with the static
  constructor it should run.
- A default interface method called on a struct through a generic constraint
  runs on a box of the value, as .NET runs it. It received the value's address
  instead, so `IBinaryInteger<T>.WriteBigEndian` and `WriteLittleEndian` threw
  `InvalidCastException` for every integer type in generic code, and a default
  method that read an interface property returned 0.
- At `O3`, `GetType().Name`, `Namespace`, `FullName` and a type's `ToString()`
  return the type's name again (issue #153). They threw "Compiler-generated
  runtime type-name facts are missing", so a `catch` block that read an
  exception's type name raised a second exception. Setting an element through
  the non-generic `IList` indexer of a `List<T>` also compiles at `O3`; it
  stopped with `NW1002` in 0.10.6.

## WIT bindings

- Interfaces are identified by the name the world gives them:
  `namespace:package/interface@version`, without `@version` for an unversioned
  package, or the world's own name for an interface it declares inline
  (`import api: interface { ... }`) or names itself (`import calc: math;`).
  Worlds with inline interfaces and unversioned packages now generate and
  compile; `netwasm-wit-bindgen` stopped with a `NullReferenceException` on an
  inline interface before. Bindings generated by earlier releases are
  rejected with a message that says to regenerate them.
- Generated names stay unique when two interfaces, types or exported functions
  share a name; only the colliding ones are qualified.
- Unsupported WIT (asynchronous functions, `future`, `stream`, `map`, an
  interface placed twice) stops with a diagnostic that names the item.
- Generated files name the generator version, and the docs install the
  standalone tool at the project's NetWasm version in a local tool manifest.
- `NetWasmWit` bindings regenerate when the NetWasm version changes, including
  an upgrade through `global.json`, and in a `WitWebWorker` project a WIT
  package directory sees NetWasm's platform package, as the worker's own WIT
  does.

## Browser projects

- `dotnet run` runs what `dotnet publish` produces. A `JsModule` or
  `WitWebWorker` project, or an application published with
  `NetWasmPublishTarget=browser`, publishes to a staging directory and is
  served on `http://localhost:5080/` until you stop it; it reported that its
  `OutputType` is `Library` before (issue #140). See
  [Run a browser project](../sdk-quickstart.md#run-a-browser-project).
- A published page works outside a secure context, for example over plain HTTP
  from a phone on the local network. Its host no longer reads `crypto.subtle`
  while it is imported, and checks the files it loads in JavaScript where the
  browser has no `crypto.subtle` (issue #139).
- In a browser without the WebAssembly exception handling and SIMD that
  NetWasm output uses, `open()` and `run()` fail with
  `NetWasmUnsupportedBrowserError`, which names them and the oldest supported
  browsers, instead of a compile error that names an opcode.
- A `NetWasmJavaScriptModule`, `NetWasmApplicationImport` or `NetWasmWit` item
  whose file does not exist stops the build with `NWSDK093`, `NWSDK095` or
  `NWSDK096`, naming the item and the path; a missing JavaScript module was
  published as an import of the build machine's path (issue #141). A failing
  bundler reports the import it could not resolve.
- Publishing a solution publishes its NetWasm libraries as class libraries are
  published, and `IsPublishable=false` skips one; a library failed it with
  `NWSDK018` (issue #143). An application's publish leaves out the managed
  assemblies of the projects and packages it references, which its module
  holds.
- `dotnet publish --no-build -p:NetWasmPublishTarget=browser` publishes a built
  application; it failed with `NWSDK082`.

## SDK and templates

- New projects name the SDK version in the project file,
  `<Project Sdk="NetWasm.Sdk/0.10.7">`; to upgrade, change that version. The
  [SDK quickstart](../sdk-quickstart.md#7-upgrade-netwasm) describes upgrading,
  including projects that set the version in `global.json`.
- The WIT worker template generates its bindings during the build with a
  `NetWasmWit` item.
- The print-`42` component published at `Oz` is 37,789 bytes with Compact
  (38,919 in 0.10.6), 40,746 with NetWasmGC and 33,762 with Bump: 29.5% smaller
  than Rust's size profile. See [Size measurements](../size-and-methodology.md).
- CoreLib follows .NET 11 RC3, and the C# 15 toolchain is the RC3 SDK.
- A culture-sensitive `StringComparison` throws `PlatformNotSupportedException`
  on `string`, `char`, `Rune` and `StringComparer.FromComparison`, as it
  already did on spans, since NetWasm compares text ordinally; `string`, `char`
  and `Rune` threw `ArgumentException`. A value outside the enumeration still
  throws `ArgumentException`. See [CoreLib and runtime](../corelib-runtime.md).
