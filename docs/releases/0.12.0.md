# NetWasm 0.12.0: WASI 0.3, with files, sockets and HTTP services

NetWasm 0.12.0 is available on NuGet.org.

Components now target WASI 0.3, whose async functions, streams and futures
let C# `async` code run on the Component Model directly. Ordinary .NET APIs
reach much more of WASI with it: files and directories, sockets and DNS,
`ws://` WebSockets, the full `HttpClient`, and HTTP services written as one
`Handle(HttpRequestMessage)` method that Wasmtime, Spin and wasmCloud run
unchanged.

## WASI 0.3

- Components import WASI 0.3.2 (`wasi:cli`, `wasi:clocks`, `wasi:random`,
  `wasi:filesystem`, `wasi:sockets`, `wasi:http`) and use the Component
  Model's async ABI. A component imports only what the program uses: the
  `dotnet new netwasm-app` program that prints 42 publishes a 37,025-byte
  component, 2,126 bytes smaller than with 0.11.3.
- They run in Wasmtime (`wasmtime run -Wcomponent-model-async -Sp3 App.wasm`,
  `wasmtime serve -Sp3 -Scli`), Spin, wasmCloud, NetWasm's Node.js launcher
  and NetWasm's browser hosts. jco 1.41 and preview3-shim 0.13 replace
  preview2-shim in the Node.js and browser hosts.
- Breaking: NetWasm no longer produces WASI 0.2 (Preview 2) components. An
  application whose host runs only Preview 2 can stay on 0.11. NetWasm never
  uses WASI Preview 1; an engine without the Component Model can load a plain
  core module (below), which has no WASI.
- `async Task Main` and `async Task<int> Main` need no setting. Breaking:
  `NetWasmComponentContract` is gone, and a project that still sets it fails
  with `NWSDK025`, which says to remove it
  ([#180](https://github.com/zion-sati/NetWasm/issues/180)).
- Synchronous .NET I/O APIs work over WASI's asynchronous operations on hosts
  that can suspend. Where the Component Model forbids blocking, such as inside
  a synchronous WIT export before it returns, a blocking call throws
  `InvalidOperationException` naming the asynchronous alternative.
- Every system service behind .NET's APIs (console, clocks and timers, random
  numbers, environment, files, networking) is a platform service, which an
  application can replace with its own.

## Files and directories

- `File`, `FileStream`, `Directory`, `FileInfo`, `DirectoryInfo` and `Path`
  work over `wasi:filesystem` within the directories the host grants, ported
  from .NET 11's Unix implementation.
- `dotnet run` and `dotnet test` grant the working directory, read-write at
  its own path, and a private temporary directory at `/tmp`, so relative paths
  and `Path.GetTempPath()` behave as on desktop. A published command takes
  `--dir HOST[::GUEST]` (`node netwasm.host.mjs --dir ...`, or Wasmtime's own
  `--dir`).
- In browsers, a page or worker mounts a picked `File`, a `Blob` or an OPFS
  directory, and writes changes back with `sync()`
  ([#142](https://github.com/zion-sati/NetWasm/issues/142)).

## JavaScript hosts

- Breaking: an execution request's `grants` names `workingDirectory` and
  `temporaryDirectory` explicitly. Only the local launcher mounts them; a
  browser request sets both to `false`.
- Output that an export writes reaches `stdout` and `stderr` asynchronously,
  after the export returns, since it crosses a WASI 0.3 stream.

## Networking

- `Socket`, `TcpClient`, `TcpListener`, `UdpClient`, `NetworkStream` and
  `Dns` run over `wasi:sockets`, ported from .NET 11 with its Unix behaviour,
  including dual-mode IPv6 sockets.
- `ClientWebSocket` connects to `ws://` servers, with .NET's managed RFC 6455
  framing over a socket as on desktop. `wss://` waits for WASI's TLS
  interface.
- Not available: non-blocking sockets, socket timeouts, `Poll` and `Select`,
  Unix domain sockets, multicast and broadcast, binding a dual-mode socket to
  the IPv6 wildcard, and reverse DNS.

## HttpClient

- `NetWasm.System.Net.Http` 0.12 is upstream .NET's `HttpClient`, request,
  response and content types over a `wasi:http` 0.3 client, so
  `GetStringAsync`, `GetByteArrayAsync`, `GetStreamAsync`, `DeleteAsync`,
  `PatchAsync` and the rest are there
  ([#179](https://github.com/zion-sati/NetWasm/issues/179)).
- Programs that use `HttpClient` run in Wasmtime (`-Shttp`), Spin, wasmCloud
  and NetWasm's hosts ([#181](https://github.com/zion-sati/NetWasm/issues/181)).

## HTTP services and components

- `<OutputType>Component</OutputType>` builds a component that exports a WIT
  world: NetWasm's `service` world, or your own with `NetWasmWitPath`. It
  publishes one `<AssemblyName>.wasm`.
- With `<NetWasmWorld>service</NetWasmWorld>` and `NetWasm.System.Net.Http`,
  the component is a `wasi:http` service: implement
  `public static partial Task<HttpResponseMessage> Handle(HttpRequestMessage request)`
  in the project's root namespace, and the package generates the handler that
  converts each request and streams the response back. An exception answers
  with a 500. `wasmtime serve`, Spin and wasmCloud run the published file
  unchanged, and `Handle` can use `HttpClient`.
- `dotnet new netwasm-serverless` creates one, with a README that serves it
  from each host.
- `dotnet run` does not run a component; it fails with `NWSDK103`, which says
  how to publish and host it. Node.js cannot serve WASI 0.3 HTTP components
  yet: jco and preview3-shim do not serve them correctly, and the problems are
  reported upstream.
- `<OutputType>CoreModule</OutputType>` builds a plain core module for an
  engine without the Component Model, such as a game's plugin host: a world's
  imports and exports become core imports and exports with the canonical ABI,
  and the module has no WASI.

## WIT bindings

- An `async func` binds to a method returning `Task` or `Task<T>`. A received
  `stream<u8>` is a `Stream`, other streams are `IAsyncEnumerable<T>`, and a
  `future<T>` is a `Task<T>`. A component runs one call of its async exports
  at a time.
- An export can receive and return an imported resource
  ([#197](https://github.com/zion-sati/NetWasm/issues/197)).
- Packages and worlds named with a `%`-escaped WIT keyword can be selected
  ([#198](https://github.com/zion-sati/NetWasm/issues/198)).

## Node.js

- `node netwasm.host.mjs [arguments]` runs a published folder without
  `dotnet`, with `dotnet run`'s defaults; a deployment that uses `HttpClient`
  carries its Node.js client, so the folder runs with `node` alone
  ([#177](https://github.com/zion-sati/NetWasm/issues/177)).
- `NetWasmJavaScriptHosts` takes `node`: a `JsModule` publishes
  `<AssemblyName>.node.mjs`, whose `open()` gives Node.js code, such as a
  serverless function's handler, the module's C# exports
  ([#178](https://github.com/zion-sati/NetWasm/issues/178)).

## Upstream

- CoreLib ports follow .NET 11 RC3 (dotnet/runtime `474ed963`), and the
  desktop oracles that tests compare against run on .NET 11 RC3.

## Compiler

- A loop that reads an array or span at its counter (`span[i]`, `span[i + 1]`)
  moves a reference along with the counter instead of scaling the counter for
  every read (`NetWasmManagedLoopStrengthReduction`, on from O1). Summing a
  span of bytes, shorts, ints or longs takes 32 to 36% less time, and
  `Span<char>.SequenceCompareTo` over 3,000 elements 36% less.
- A branch that the ranges of its operands decide, such as a fallback loop
  that can never run, is removed with the code only it reaches
  (`NetWasmManagedRangeBranchFolding`, on from O1).
- A field access or virtual call on an object `newobj` just produced is not
  null checked, from O1; at O3, Os and Oz neither is one on the `this` of a
  constructor that only `new` and other constructors call, F#'s included
  (`NetWasmManagedNewObjectNullCheckElimination`,
  [#206](https://github.com/zion-sati/NetWasm/issues/206)).
- Small copies of structs that hold a `ref` field, such as spans, read in
  chunks no wider than their alignment, so the processor can forward the
  field stores that built them.
- Static data starts above the first KiB of memory, as Emscripten lays it out,
  and `NetWasmOptimizerLowMemoryUnused` (`nwc -lowmemoryunused`) lets wasm-opt
  fold constant address offsets into loads and stores. It is off by default:
  Wasmtime's code for the folded addresses was slower in more cases than
  faster, on both an Apple M1 Max and an Intel Core i5-12600K.
- `Activator.CreateInstance<T>()`, and `Lazy<T>`, `LazyInitializer` and
  `ConditionalWeakTable.GetOrCreateValue`, which use it, compile for any `T`.
  A type without a public parameterless constructor fails when the call runs,
  with .NET's exception, instead of stopping the build with `NW1003`, so
  `new Lazy<string>(() => "x").Value` builds. A class whose parameterless
  constructor is private or protected is no longer constructed, as on .NET
  ([#212](https://github.com/zion-sati/NetWasm/issues/212)).
- NetWasm is tested with Wasmtime 50.0.1 (0.11 used 49.0.3).

## Allocation

- With NetWasmGC, an object, box (including a boxed `Nullable<T>`), delegate
  or string below 256 bytes is allocated by advancing a pointer through a
  pre-zeroed run of its size class, and the collector is called only to refill
  a run. At O1 to O3 that step is inlined into compiled code; small arrays take
  the same path inside the runtime. On an Apple M1 Max under Wasmtime 50.0.1,
  against the same compiler without it (21 interleaved samples, every result
  matching desktop .NET), a binary-trees benchmark that allocates millions of
  small objects takes 28% less time at O3 and 32% less at Oz, a UI churn
  workload 25% and 38% less, a retained object graph 14% and 24% less, boxing
  `Nullable<int>` values 40% and 31% less, and a transaction workload that
  allocates as it goes 4% and 5% less.
- Compiled code publishes each allocation's GC roots once rather than up to
  three times, and at O1 to O3 only when an allocation has to call the
  collector. Components with Compact are 3 to 5% smaller and allocate 1 to 2%
  faster at O3. With NetWasmGC they are 3% smaller at Oz; at O1 to O3 the
  inlined allocation outweighs the saving, and they are 2 to 3% larger.
- Behaviour change: with NetWasmGC, `GC.GetTotalAllocatedBytes` counts the
  slots that allocations occupy, as the collector's live-byte figures already
  did: an object below 4 KiB takes the smallest multiple of 8 bytes above its
  size. Compact and Bump still count requested bytes.

## Performance

Figures are from the micro-benchmark runner at `O3` with NetWasmGC under
Wasmtime 50.0.1 on an Apple M1 Max, against 0.11.3 built the same way.

- Across 2,213 cases the geometric mean is 0.6% lower (0.994), and cases that
  take over a microsecond are 1.7% faster. 90 cases take more than 5% less
  time, most of them span, memory and loop cases.
- Span and memory cases are 1.8% faster overall. `ReadOnlySpan.IndexOfString`
  with one match takes 6% more time, since it copies spans in two halves now.
  On an Intel Core i5-12600K, measured before the WASI 0.3 work, the span
  copies and the null check changes made 214 span and memory cases more than
  5% faster.
- Six cases are 6 to 14% slower from where Wasmtime places their code: five
  vector cases of 4 to 10 ns whose code is the same instructions as 0.11.3's,
  and Benchstone's `MatInv4`, which takes between 1.00 and 1.09 times 0.11.3's
  time as its code moves by a few bytes. With epoch interruption, which moves
  code within functions, all six match or beat 0.11.3.
- [Performance](https://github.com/zion-sati/NetWasm/blob/main/docs/performance.md#name-functions-in-a-profile)
  describes how to name functions in a profile with a diagnostic build that
  keeps them (`NETWASM_KEEP_NAMES`).

Rebuild an application to pick up the changes.
