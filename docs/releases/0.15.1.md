# NetWasm 0.15.1: loops in exception handlers, Math as .NET computes it

NetWasm 0.15.1 is available on NuGet.org.

This patch fixes compiler failures and miscompilations found compiling real
libraries, and makes `Math` and `MathF` compute what .NET does on WebAssembly.

## Fixes

- A loop inside a `catch` or `finally` block whose body has its own
  `try`/`catch` failed to compile with an internal error (`NW1011`), as did a
  `break`, `continue` or `return` out of a `catch` nested in such a loop
  ([#259](https://github.com/zion-sati/NetWasm/issues/259)). They compile and
  run as on desktop .NET.
- With `NetWasmOptimization=Oz`, assigning a new value to a span or other
  struct parameter could leave later reads of the parameter seeing its first
  value. It is fixed at every optimization level.
- `Math` and `MathF` gave results off by up to millions of units in the last
  place for some arguments: `Math.Log10(1000)` was 2.9999999999999996, many
  `Math.Log2` results for powers of two were inexact, and `Math.Asinh` and
  `Math.Atanh` lost precision near zero. Both are now .NET's own source, and
  their transcendental functions give the results of musl's libm, as .NET
  calls the platform's C library and as Mono's WebAssembly runtime does: from
  the C library every program links, or from C# ports of the same routines
  where those run faster and give the same bits. `double.Exp2` and
  `float.Exp2` compute exp2, as Mono's AOT build does.
- `Clamp` with a minimum above its maximum, `Sign` of NaN and `Abs` of a
  type's minimum value threw without .NET's message on most number types,
  directly and through generic math; they now throw with it, such as
  `'5' cannot be greater than 3.`, and writing the message adds no
  formatting code to a program that clamps.
- `AppContext.BaseDirectory` was empty, so code that looks for data files by
  walking up from it failed with `ArgumentException`. It is `/`, the sandbox
  root, as on Mono's WebAssembly runtime.
- Under the JavaScript host, in Node.js or a browser, much of what a program's
  calls through WASI created stayed in the JavaScript heap until the program
  ended: every byte read from a file, each write to a file, each `HttpClient`
  request (about 80 KB) and each file opened, and a cancelled timer stayed
  until the time it would have fired. A long-running program, or a test suite
  that reads data files, could run Node.js out of memory. The host now
  releases each of them once the program is done with it: a program that reads
  and writes 400 MB, cancels 50,000 timers and opens 1,000 files runs in a 128
  MB JavaScript heap, and 20,000 `HttpClient` requests in 64 MB.
- Under the JavaScript host, a program waiting on the host, for an
  `HttpClient` response or a timer, resumed up to 10 ms after the host was
  done, and file data crossed between the program and the host one byte at a
  time. The program now resumes as soon as the host is done and bytes cross in
  bulk: 2,000 `HttpClient` requests to a local server take 1.7 s instead of
  31 s, ten 20 MB file reads 0.37 s instead of 1.2 s, and 20,000 small file
  writes 1.6 s instead of 3.6 s.
- `dotnet test -- <run settings>` dropped NetWasm's own run settings, so the
  run found no tests. Both now apply, and `dotnet test --logger trx`,
  `--logger html` and `dotnet test -- --report-trx` write their reports.
- An internal compiler error (`NW1011`) now names the method it occurred in,
  and only file system failures report `NW1014`.

## Upgrading

Change `NetWasm.Sdk/0.15.0` to `NetWasm.Sdk/0.15.1` in your project. Nothing
else changes: 0.15.0's [release notes](https://github.com/zion-sati/NetWasm/blob/main/docs/releases/0.15.0.md)
describe the release this patch builds on.

## Known gaps

- Some code runs slower than with 0.15.0. Of the 2,213 cases in NetWasm's
  micro-benchmark suite (O3, NetWasmGC, Wasmtime), 25 take more than 5% longer,
  confirmed at two code alignments, while 56 take at least 5% less:
  - Some `Math` and `MathF` functions now call the C library where 0.15.0 ran
    faster managed code that, for `Log10`, `Sin` and `SinCos`, gave other
    results: `Log10` and `FusedMultiplyAdd` take about 1.12 times as long,
    `MathF.SinCos` 1.09 and `Sin` 1.06. Floating-point programs built on them,
    such as the Whetstone benchmark, take up to about 1.16 times as long.
  - Creating a rotation with `Matrix3x2`, `Matrix4x4` or `Quaternion` takes 1.2
    to 1.7 times as long: `float.SinCos` returns its two results through memory.
  - Eight cases, among them 64- and 128-byte block initialization and
    `Span<char>.Reverse`, run the same code as with 0.15.0 and take 1.1 to 1.6
    times as long, which points to where their data lands in memory.
