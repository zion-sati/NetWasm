# NetWasm 0.10.3: faster interop and smaller apps

NetWasm 0.10.3 is available on NuGet.org.

This release makes calls between C# and JavaScript much cheaper and lets an
application pay only for what it uses. A synchronous `[JSImport]` with scalar
parameters is now a direct WebAssembly import, spans reach JavaScript without a
copy, and `[WasmImportLinkage]` calls host functions directly. A page
application's runtime bundle holds only what the application links, and
formatting a number no longer pulls in formatting code the program never
calls. The print-`42` component is 38,919 bytes, 27.4% smaller than Rust's
size profile.

## JavaScript interop

- A synchronous `[JSImport]` whose parameters and result are primitive scalars
  or `void` is a direct WebAssembly import: the arguments are its parameters
  and the result is its return value. A host failure, including a result
  outside the managed type's range, still raises `JSException`. The per-call
  checks on the shape of each request and result object are gone for every
  call. Measured in Node, the `ulong CreateNode(uint)` call from issue #115
  went from 2,281 ns to 101 ns per call without the checks, and a direct
  import takes it further: a managed loop calling `int Add(int, int)` drops
  from 102 ns to 13 ns per call.
- A synchronous `[JSImport]` can take a `Span<T>` or `ReadOnlySpan<T>` of any
  number-array element type. JavaScript receives the typed array it gets for
  `T[]`, as a view of the span's memory valid until the call returns, so
  nothing is copied and writes to a `Span<T>` view reach the managed buffer.
  Spans over arrays, `stackalloc` memory and `NativeMemory` all work. Number
  arrays still copy. An asynchronous `[JSImport]` with a span parameter fails
  the build. See [Choose a copy or a view](../javascript-interop.md#choose-a-copy-or-a-view).
- A `[JSExport]` declared in a referenced `netwasm0.1` class library is
  exported, as in .NET, so a library can ship the callbacks its JavaScript host
  calls. Before, it was left out of the published module, its declarations and
  `interop.json` without an error. An export name declared twice fails the
  build with an error that names both declarations and their assemblies.

## Direct host imports

- A `[LibraryImport]` or `[DllImport]` with `[WasmImportLinkage]` imports its
  entry point from the module its library name gives. The host supplies the
  function through the `modules` option of the generated `open()` or a bundled
  `NetWasmJavaScriptModule`, and a throw from it raises `JSException`.
- A native archive can import from a module the project declares with
  `<NetWasmImportModule>` or a registered `NetWasmJavaScriptModule`, using the
  C attributes `import_module` and `import_name`. An import from an undeclared
  module fails with NWPACK001 naming the import and the fix. A component build
  with an import module stops with NWSDK087, because a component imports
  through WIT.

See [Call host functions directly](../static-native-interop.md#call-host-functions-directly).

## Smaller applications

- A page or worker application's runtime bundle is generated from what the
  application links: only the WASI shim families it imports, a filesystem only
  when it links a filesystem interface, and only the platform providers it
  reaches. Each WIT import's canonical-ABI code is generated at build time
  instead of being interpreted at run time, and Release builds leave out the
  deployment manifest validator (set `NetWasmValidateDeploymentManifest` to
  `true` to keep it). The template page application's `netwasm.page.mjs` drops
  from 313,711 to about 192,000 bytes, and from 58,751 to about 37,300 bytes
  with Brotli.
- The runtime's type registrations live in one shared initialization function
  instead of being copied into every entry. Each additional `[JSExport]` used to
  carry the registrations of every type in the program; in the reproducer from
  issue #123, three more exports in a program with 20 extra types now add 176
  bytes instead of 1,290.
- `int.ToString()` no longer runs the floating-point formatting tables'
  initialization, `float`, `double`, `Half` and `BFloat16` `ToString()`
  without a format no longer reach the custom format-string parser, and
  interpolated strings no longer reach every primitive's formatter for each
  hole. On wasm32, `$"i={value}"` with an `int` goes from 255,060 to 26,543
  bytes, `float.ToString()` from 101,978 to 55,061 and `int.ToString()` from
  16,309 to 11,880. `string.Create(provider, ...)` now passes its provider to
  the interpolation handler, as on desktop .NET.

The print-`42` component published at `Oz`:

## WIT bindings

- A `NetWasmWit` item generates C# bindings for a WIT file or package directory
  during the build, with optional `World`, `Namespace` and `Accessibility`
  metadata, in an application or a class library. It needs no Node.js
  installation. See [Generate bindings during the build](../wit-bindings.md#generate-bindings-during-the-build).
- A world may declare its own types, such as `type` and `enum` items, and
  resources. The binding tool stopped with "unsupported WIT world item" on
  them.
- A world's direct imports share one partial imports class. Before, each import
  was written into its own class of the same name, which did not compile with
  more than one.
- `[WitImport]`, `[WitExport]`, `[WitPostReturn]` and `[WitResource]` take one
  argument for a world's own functions and resources. The two-argument form
  with an empty interface name fails the build and names the one-argument
  form; regenerate bindings made by an earlier tool.
- `netwasm-wit-bindgen` reads WIT from standard input with `--wit -`, including
  a shell's `--wit <(command)` pipe, writes to standard output with
  `--output -`, and sets the generated namespace with `--namespace`.

## Libraries

- `Convert.ChangeType(object?, Type)` and
  `Convert.ChangeType(object?, Type, IFormatProvider?)` follow .NET's
  semantics.
- An enum's `IConvertible.ToType` converts to its own type, to `Enum` and to
  `object`, as in .NET, instead of to its underlying type.
- `System.Threading.Lock`, `ConcurrentQueue<T>`, `ConcurrentBag<T>` and
  `IProducerConsumerCollection<T>` are available. As with `Monitor`, an
  application's single managed thread always acquires a lock.

## Fixes

These failures are present in 0.10.2.

- Converting a boxed enum could overwrite the value while dispatch still
  checked the remaining enum types, and a narrowing conversion, such as a
  `long`-backed enum to `int`, truncated instead of throwing
  `OverflowException`.
- A generic method whose `try` is unreachable for its type arguments, as in
  `double.CreateChecked<double>` under LINQ's `Sum` over `double[]`, failed to
  compile at `O3` with NW1002.
- A .NET SDK built by a Linux distribution reports a distribution runtime
  identifier, such as `fedora.43-arm64` or `rhel.9-arm64`, so restore failed
  with NWSDK041. The SDK now selects the host tools by the portable runtime
  identifier, and restore succeeds on Arch, Fedora and RHEL.
- A build with an SDK that cannot restore `netwasm0.1`, the 10.0.1xx band that
  Linux distributions package, failed with a NuGet error. It now stops before
  restore with NWSDK086, naming the SDK and where to get a supported one.

## Compatibility

- The interop manifest is version 2 and the generated raw adapter's interface
  is version 2. Rebuild and publish an application with the 0.10.3 SDK and
  serve its published files together, as before.
- Release page and worker bundles no longer validate the deployment manifest's
  shape at startup. The build validates it, and the loader still checks it
  against the SHA-256 that `open()` pins.

## Validation

- New tests compile and run the changes on wasm32 and wasm64 and compare
  results with desktop .NET, including span views in Chromium, Firefox and
  WebKit, generated canonical-ABI code for each WIT type family, library
  exports, the shared runtime initializer and pay-for-play formatting.
- SDK consumer qualification builds WIT bindings from a library under paths
  with spaces on every host, publishes a page module that references a library
  export, and caps the published page runtime at 210,000 bytes.
- The release workflow runs the complete compiler test suite with each
  fixture's full matrix and checks merged coverage against the baseline.
