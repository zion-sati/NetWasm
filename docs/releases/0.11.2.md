# NetWasm 0.11.2: faster delegate calls and span loops, and a compiler that needs half the memory

NetWasm 0.11.2 is available on NuGet.org.

This release makes delegate calls and folds over spans faster, and the
compiler itself uses less than half the memory it did. Figures below are from
the micro-benchmark runner at `O3` with NetWasmGC on an Apple M1 Max, against
0.11.1 built the same way.

## Faster code

- A delegate call now enters a small invoke function, which calls a
  single-cast delegate's target directly. A delegate with an invocation list
  goes on to a separate multicast function that is never inlined into it, so
  the common call no longer pays for the list's loop: on arm64 the shared
  function saved six callee-saved registers on every call.
  `DelegatePerf.DelegateInvoke` takes 38% less time,
  `MulticastDelegateInvoke` 44% less, `LowLevelPerf.StaticDelegate` 47% less
  and `InstanceDelegate` 34% less. Code that calls delegates in its inner
  loops gains with them: LINQ's `Where` benchmarks take 22 to 24% less time
  and `Count` 29% less.
- At `O1` to `O3` each multicast function carries its own copy of the target
  dispatch. `None`, `O0`, `Os` and `Oz` call the invoke function for each
  entry instead, which keeps the module smaller.
  `NetWasmManagedMulticastInlineDispatch=Enabled` or `Disabled` (`nwc
  -managedmulticastinlinedispatch:Enabled`) overrides the preset.
- A fold over a span, such as `foreach (var value in span) sum += value | 1;`,
  runs four elements at a time with Wasm SIMD, as the same loop over an array
  already did. The span indexer's check of each index moves in front of the
  loop: when every index the loop will read is in bounds, the loop runs as
  vectors; otherwise it runs element by element and throws where it would
  have. `StrengthReduction.SumIntsSpan` takes 43% less time.
- A store to a rectangular array element, such as `grid[i, j] = value`, checks
  the array for null once instead of twice. `MDArray2` takes 9% less time and
  `MDXposMatrix` 6% less.

The runner calls each benchmark case through an `Action` delegate, so the
faster call takes about 1.5 ns off every case. Cases that take under 20 ns run
24% faster (geometric mean) mostly for that reason; across cases that take
over 1 µs the geometric mean is 0.986. No case is slower at both function
alignments the gate times. Two are slower at one only: `MDMidpoint` by 9% at
4 KiB alignment and not at 128 bytes, and `Span.IndexerBench.WriteViaIndexer1`
by 6% and 2%. Their hot loops compile to the same code in both releases, apart
from register names, so the difference is code placement.

## A leaner compiler

- The compiler, `nwc`, now collects garbage with
  [Satori](https://github.com/VSadov/Satori), a concurrent collector with
  thread-local collections of the youngest generation, instead of the .NET
  server collector. Compiling DoomSharp's browser build, its peak memory falls
  from 2.0 GB to 0.7 GB at `O0` and from 3.4 GB to 1.5 GB at `O3`. The `O0`
  compile of the inner development loop takes the same time; an `O3` compile
  takes 5% longer. The compiled modules are byte-identical.

## Fixes

- Indexing a multidimensional array with an `nint`, as in `grid[n, k]` or
  `new int[n, m]` with `nint` values, failed with NW1002. ECMA-335 lets
  `native int` and `int32` convert implicitly where a value is passed to a
  call, stored to a local, argument or field, or returned; NetWasm now accepts
  those conversions and makes each one explicit for the code it generates
  ([#196](https://github.com/zion-sati/NetWasm/issues/196)).

## Benchmarks

The published benchmarks now build with `NetWasmOptimizerConverge=true`, which
repeats `wasm-opt`'s passes until the module stops shrinking, as a CI release
build can afford to. It stays off by default.
