# NetWasm 0.12.2: calls that cost the same however much is alive

NetWasm 0.12.2 is available on NuGet.org.

This patch makes a call into a program, and the runtime's bookkeeping for
finalizers, weak references, GC handles and pending asynchronous work, cost the
same however much the program keeps alive.

## Fixes

- A call into a JavaScript module, each callback of an asynchronous `Main`,
  and each turn of a module's event loop ran a full garbage collection when
  the program had a finalizer, which one `async` method that can throw is
  enough to bring in. Since 0.12.0 a module's export call collected twice,
  once at its own end and again in the event loop's turn after it. A call now
  leaves collection to allocation, as desktop .NET does, and runs only the
  finalizers of objects a collection has already found unreachable. In the
  issue's page at `O3`, a no-op export with 10,000 small arrays alive takes
  0.2 µs instead of 297 µs, and 10,000 calls run no collection instead of
  20,000 ([#216](https://github.com/zion-sati/NetWasm/issues/216)).
- Registering a finalizer, a weak reference, a `ConditionalWeakTable` entry
  or a `GCHandle` took time in proportion to how many of its kind were alive,
  and running pending finalizers searched all of them for each one. With
  16,000 alive, a finalizable allocation took 27 µs and a `WeakReference`
  more than 90 µs. Each now takes well under a microsecond however many are
  alive. Weak references, timers, sockets and files all register a finalizer,
  so programs that keep many of them gain the most.
- With many asynchronous operations pending, such as a service's open
  connections, each completion took time in proportion to them, since the
  event loop searched its pending work and the JavaScript host searched its
  waiting handles. Both now find the completed operation directly.
- The JavaScript hosts took queued stream chunks, the handles of managed
  objects JavaScript has collected, and the calls a worker client queued while
  its worker started from the front of an array, which costs time in
  proportion to what is left once the queue is long: 200,000 queued items took
  7 to 17 seconds. A program reading a large chunk the host supplied, such as
  a file or a response body, a few kilobytes at a time also copied the rest of
  the chunk on every read. Each item and byte now moves once.

The `Console.WriteLine(42)` component is 38,168 bytes with the default Compact
collector, 662 more than with 0.12.1, for the runtime's constant-time
registries.
