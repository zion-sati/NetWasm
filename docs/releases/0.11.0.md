# NetWasm 0.11.0: rebuilds that compile only what changed

NetWasm 0.11.0 is available on NuGet.org.

This release cuts the time from saving a file to running the change.
On DoomSharp's browser build, on an Apple M1 Max, a Debug rebuild after an
edit to one method takes 1.6 s, where 0.10.8 took 29.3 s. Release rebuilds
take 35 s at `Oz` and 61 s at `O3`, where they took 183 s and 222 s, and a
clean build is 2.6 to 5.3 times as fast at every level.

## Rebuilds compile only what an edit changes

- Debug builds compile at `O0` and keep each method's compiled code under
  `obj/`. The next build compiles only the methods an edit affects and reuses
  the rest. A kept method is reused only while everything its code was built
  from still holds: its body, the methods and types it uses, and the target.
- When an edit changes only method bodies, and each edited method still uses
  what it used before, the build patches the last module with the edited
  methods instead of compiling the program again.
- `NetWasmCompiledUnits=false` compiles every method each time.
  `NetWasmCompiledUnits=true` keeps compiled code at the optimizing levels
  too, where it is reused but the module is always compiled in full.
  `NetWasmVerifyCompiledUnits=true` also compiles every reused method and
  fails the build if the two differ. `nwc` takes `-compiledunits+`/`-` and
  `-verifycompiledunits+`.
- A damaged or replaced store, such as one an IDE build and a command-line
  build share, costs reuse only: the build compiles the methods again.
- The compiler's earlier per-method cache of analysis results, which every
  library edit rewrote in full, is gone; compiled units replace it.
- Breaking, for hosts of `NetWasm.Compiler.Browser`:
  `CompilerOptions.EnableFrontendCache` and the session's prepare and publish
  calls are gone. A `BrowserCompilerSession` reuses an `O0` compilation's
  units when `CompilerOptions.CompiledUnits` is set and
  `CompilerOptions.IntermediateOutputPath` names them; it keeps them in
  memory, and `ExportCompiledUnits` and `ImportCompiledUnits` carry them to a
  later session, for example through IndexedDB.

## `dotnet watch`

- `dotnet watch` runs on NetWasm projects. Its design-time builds failed with
  `NWSDK037`, then `MSB4006`.
- The development server that `dotnet run` starts for a browser project stays
  up for the whole `dotnet watch` session. Each rebuild after a save updates
  the site it serves, and the pages it serves reload themselves when the
  build ends.
- The server serves each file from where the build leaves it, at the path
  `dotnet publish` copies it to, so a rebuild no longer publishes the site
  into a staging directory.
- Breaking: a file that a target copies into the publish directory after
  `Publish` reaches the published site but no longer the served one. Declare
  such files during the build as `NetWasmSiteFile` items with the `SitePath`
  they are served at; see
  [Run a browser project](https://github.com/zion-sati/NetWasm/blob/main/docs/sdk-quickstart.md#run-a-browser-project).
  `dotnet publish` copies each declared file.

## Faster builds

- The compiler's and runtime pack's build tasks run in MSBuild's own process
  on .NET. Each task call started a process of its own, about 13 in each
  browser build. MSBuild on .NET Framework, as in Visual Studio, keeps the
  task host, as does a build that sets `NetWasmIsolateBuildTasks=true`.
- The runtime is merged into the application in one pass that copies the
  application's code and rewrites only the indices that move, instead of
  Binaryen's `wasm-merge`, which reads and writes the whole module. The host
  tools no longer carry `wasm-merge`, and `NETWASM_WASM_MERGE_PATH` is no
  longer read.
- The host tools carry a native `wasm-tools` 1.256.0 from its upstream
  release, which validates and packages modules without starting Node.
  `NETWASM_WASM_TOOLS_PATH` overrides it with the same release.
- `nwc` is a self-contained Native AOT executable built for .NET 11. It uses
  the server collector, sized so that a compile usually finishes without a
  collection, at the cost of a larger peak working set. A build that sets
  `DOTNET_GCgen0size` or `DOTNET_GCLOHThreshold` keeps its own values.
- `nwc` analyzes each method once across the rounds in which it removes
  unreachable code at `O1` and above, and runs more of its work on all cores.
- Each project's build environment, the verified packages and tools it
  resolves, is kept under the user's local application data and shared
  across projects and clean builds.

## Optimization

- `Vector3` values stay in SIMD locals, as `Vector2` and `Vector4` values
  already did. Every `Vector3` temporary and argument used to go through
  linear memory. On an Intel i5-12600K, `Vector3`'s operators take 4.6 to
  5.4 ns (from 7.0 to 7.3), `Dot` and `Distance` 4.9 ns (from 7.8), and summing
  a 256-element `Vector3[]` 132 ns (from 820). On an Apple M1 Max, with each
  operation in a method of its own, `+` takes 3.4 ns (from 10.3), `Cross`
  2.8 ns (from 12.2), `Dot` and `Distance` 3.4 ns (from 6.1 and 6.3), the
  array sum 201 ns (from 1,916), and stepping 256 particles 598 ns (from
  3,794). `Vector2` and `Vector4` code is unchanged.
- SIMD vectors' value-frame slots are aligned as RyuJIT aligns their stack
  homes: 8 bytes for `Vector2`, 16 for the 12- and 16-byte vectors. An access
  no longer straddles a cache line, which had made `Vector3`'s operators take
  8 or 18 ns on the i5-12600K depending only on where the frame stack landed.
- `wasm-opt` runs each preset's passes once over the linked module.
  `NetWasmOptimizerConverge=true` (`nwc componentize -converge`) repeats them
  until the module stops shrinking, as every build did before. On DoomSharp,
  converging took the optimizer about twice as long for a module 0.04% (`Oz`)
  to 0.12% (`O3`) smaller, which rendered no faster. Console 42's `Oz`
  component is 39,230 bytes, 59 more than with convergence.

## SDK and templates

- The templates no longer carry a `global.json`, so a generated project
  builds with whichever .NET SDK `dotnet` selects, including .NET 11. NetWasm
  still requires SDK 10.0.303 or newer.

## Testing

- Each preview release also compiles the compiler's corpus with compiled
  units under verification: every reused method is compiled again and
  compared, and each module must equal the one a plain compile gives.
- [`compiler-qualification/micro-benchmarks/`](https://github.com/zion-sati/NetWasm/blob/main/compiler-qualification/micro-benchmarks/README.md)
  reproduces the [micro-benchmark results](https://github.com/zion-sati/NetWasm/blob/main/docs/micro-benchmarks.md):
  dotnet/performance at a pinned commit and NetWasm's own workloads, built
  for desktop .NET 11, Mono AOT and NetWasm and timed interleaved.

Rebuild an application to pick up the changes.
